# FloraLab 产品优化方案

基于正式线上 1.5.2、桌面 1440×1000 / 手机 390×844 的实际使用与截图，以及同类产品官方资料。代码基础优化交付版本为 1.5.3。以下保留原始优化方案；1.6.0 已实现核心创作流程，具体交付范围见 docs/release-1.6.0.md。未列入该发布说明的能力仍属于后续路线。市场对比基于公开资料，未购买或登录竞品后台，不作市场份额、转化率或优劣评分推断。

## 1. 产品判断与目标

FloraLab 的核心价值是：让一个想法逐渐成为自己愿意做、也能真正做出来的具体作品，并保留每次选择的依据。

目前材料、数量、结构、版本与制作记录已有基础，主要缺口是用户不容易理解当前结果、判断变化、选定方向、接回真实制作。首页的成品照片与工作区的细线圆点之间存在视觉落差；大量专业名词、分散的状态和不明确的操作后果增加了学习成本。

优先服务两类场景：个人创作者做礼物或桌花；小型花艺工作者探索单件作品并核对材料。专业用户可直接导入已有方案、进入材料或结构，任何阶段都可以返回探索。团队活动统筹、客户合同、支付、销售库存和多人协同先列为扩展方向。

成功结果应当是：用户能说明自己选了哪件作品、哪些事实已确定、下一步需要准备什么；完成后，真实照片、材料变化和复盘仍属于同一件作品。

## 4. 信息架构与主路径

全局导航建议为“我的作品 / 材料库 / 新建”，安装和导入说明放在次级入口。创作空间入口说明它会打开哪里、需要带什么文件，避免让人以为站内已经提供完整聊天或生图服务。

作品内部以四个任务区组织：

| 任务区 | 主要内容 | 首要操作 |
| --- | --- | --- |
| 想法与方案 | 原始想法、参考图、备选方向、方案对比、事实锁定 | 保存或选定喜欢的方案 |
| 材料与准备 | 材料数量、已有、需购、实际单价、花器、固定与供水 | 确认准备清单 |
| 动手制作 | 当前步骤、材料、操作图、施工图、实耗与损耗 | 完成本步 / 记录变化 |
| 成品与记录 | 成品照片、简短复盘、修改记录与可恢复快照 | 保存这次作品 |

工作区内始终展示“当前方案”和保存状态，并允许直接跳转。阶段用于接续工作，不作为强制流程：导入确定方案可直接制作；有参考图但没材料可继续探索；已完成作品仍可复制成新方案。

当前选中方案、最终制作方案、历史快照是三个不同概念。切换浏览不改变最终选定；预览不保存新版本；只有明确操作才切换制作方案。

## 5. 页面与交互规格

### 5.1 首页 / 我的作品

首次访问保留白绿品牌主图和一句用途说明，主按钮“开始一件作品”，旁边“导入已有方案”。下方用一件可浏览的示例解释能得到什么，并标注示例，避免误认为个人作品。

已有作品时，先显示“继续上次作品”，包含封面、作品名、最后修改时间、当前方案、最近任务、保存位置。所有作品可按最近修改、探索中、准备中、制作中、已完成筛选；不只展示前六件且没有其他入口。

封面优先使用用户选择的效果图或成品图；缺少图片时用清楚标注的结构缩略图。首次编辑后提示“已保存在本机”，导出入口持续可用。不能暗示已同步云端。

### 5.2 新建与要求确认

首屏只要求描述想法，可添加参考图或选择已有材料；提供“先整理一下”。形式、气质、预算、地区等可稍后补。不要预先选中会悄悄进入方案的主题色；自动建议与用户选择分开。

文字解析给出可修改的结果：颜色、形式、希望使用、明确不使用、数量、已有材料、尚未理解的描述。简单且无冲突时用行内提示继续；材料、颜色、数量冲突时明确展示冲突，不要求每次都完成冗长确认向导。

规则优先级：当前明确指令 > 已确认版本事实 > 用户这次主动选择的字段 > 自动建议。新指令与已确认版本冲突时，应明确变更范围或创建新方案；不能在后台自动解锁。

先以确定的词表和否定词处理可覆盖的输入，保留原句与解析来源；复杂意图交给创作空间讨论。不要让关键词匹配输出伪装成完整语义理解。没有把握的数量、特殊物件或颜色标为“待核对”。

### 5.3 方案探索与对比

方向卡片包含大图 / 视觉参考、简短名称、一句差别、材料变化摘要。参考图、结构示意、生成效果图、真实成品采用不同标签。没有生成图时直接说明，不把其他作品的照片当成当前成品。

先看当前方案，再展开可用方向；不固定必须六个。对比默认两件作品，同一尺度呈现结构，允许查看材料和空间变化。桌面并排，手机切换 A/B 且保持相同观察位置，避免要求记住六张长卡片。

操作名称：“查看变化”“保存为另一个方案”“选为制作方案”。应用前列出新增、移除、数量变化和保持项。结构变化也要说明高低、左右、前后或焦点的主要差别。

锁定控件使用真实开关和明确状态“允许调整 / 已锁定”。已确定方案默认保护材料种类、颜色、数量、花器、包装、特殊物件、固定与供水、主轮廓；用户可主动开放某一项，不因主题名称改变材料。

### 5.4 效果图与创作空间交接

每个方案的图片区域优先展示当前版本的效果图；首次为空时提供“带到创作空间生成”和“添加已有效果图”。交接同时提供文件与可复制约束，并说明粘贴位置和下一步。

图片回传时关联 projectId、方案 ID、事实版本和生成时的约束摘要。Recipe 或主要结构发生变化后，原图标为“基于较早版本”，保留查看和重新生成入口，不自动丢弃，也不继续称为当前效果图。

上传图只做文件与关联处理，不能自动声称已识别花材、数清枝数或检查安全。自检按材料种类、颜色、特殊物件位置、轮廓和数量密度记录；只有真实运行了检测才显示其结果。数量保持是事实约束，图片逐枝难以计数是表达限制。

### 5.5 材料与采购

清单以“需要 / 已有 / 还需购买”表达，参考价与自己的采购价分开。差额、总价和超预算原因直接显示。预算为空表示未设预算；未知价格留空并标注，不能按零元让总价显得完整。

从某一行进入材料详情后，提供“用于当前作品”或“替换此材料”的上下文操作。替换先展示材料、颜色、数量、固定、供水和结构影响，再应用。保留自定义材料，资料不足时允许记录但显示待核实。

材料照片统一缩略图容器和主体尺度，详情保留整张原图；不能裁掉识别部位来追求一致。区分具体颜色照片与可选颜色范围。季节、来源、参考价、宠物风险要有来源或核实状态。

### 5.6 施工图与动手制作

默认图形模式先呈现材料名称、作用与自然语言位置，点击后在图上高亮。精细模式再显示 XYZ、角度、长度；给出原点、单位、左右方向、长度量测基准和角度参考。五视图保持节点 ID 一致。

手机选中点位后用可收起面板显示参数，图保持可见；点选、键盘、按钮均可完成调整，拖动不是唯一方法。主节点可点击面积至少 44px；重叠节点应提供列表选择。

每个制作步骤至少包含“本步需要 / 具体动作 / 检查标准 / 下一步”。首步用实际材料预处理清单或有用示意替换大编号占位；任何补水、固定、承重指导都需有材料和结构依据，资料不足不能虚构时间或重量上限。

下一步按钮易于找到；推进步骤与登记实耗分开。实耗支持加减、直接输入和撤销，损耗记录原因可选。材料不足给出缺口与替代入口，不能自动修改 Recipe。每次修改明确是更新实际记录，还是修改设计。

### 5.7 成品、版本与恢复

成品页面先展示照片和“保存这次作品”，难度、耗时、问题可选填。照片可加“正面 / 侧面 / 细节”，手动选择对照效果图；复盘比较实际轮廓、颜色、层次、结构、材料，不生成虚构还原率。

修改记录用于说明发生过什么；快照用于恢复完整状态。恢复操作必须显示作品名称、时间、方案及将替换的内容，执行前再保存当前快照。提供“复制为新方案”作为保留两个状态的途径。

导入先检查文件结构、版本与必要字段，预览摘要后导入为独立作品；失败保留原作品。未知版本不能静默降级丢字段。未来图片附件格式升级，应先实现导入迁移与失败恢复，再启用新写入格式。

## 6. 视觉与文案原则

保留奶白、植物绿与现有字体气质。工作页面减少宣传式留白，优先让用户看到自己的作品与可操作内容。细线示意提高主体尺寸和对比度；重要状态不能只用颜色区分。

主按钮通常服务一个当前任务，次级操作与危险操作层级分明。中文作为主要产品语言：Recipe → 材料清单；Mechanics → 固定与供水；Blueprint → 摆放施工图。专业原名可在详情与导出中保留。

价格明确标注“预计需购”，不以未完成采购核对的数字暗示正式报价。自动检查结果用“发现需核对的事项”或明确条目表示，不单凭规则结果保证真实制作安全。

图片工作分三类：品牌图可生成并统一审美；材料图优先可信实拍并保留来源；方案效果图必须绑定事实版本。后两者不能为了填满界面使用漂亮但不对应的图片。

## 7. 代码架构与本轮重构

### 当前落地（1.5.3）

| 层 | 职责 | 本轮变化 |
| --- | --- | --- |
| public/app.js | 应用装配、导航、操作绑定、调用持久化与规则 | 抽出约 20KB 的页面绘制；选择节点的修正留在控制层 |
| public/views/blueprint.js | 五视图、节点说明与编辑控件的 HTML/SVG | 独立视图工厂，显式传入状态与格式化函数 |
| public/views/render.js | 效果图交接与结构展示 | 显式注入 buildRenderSpec，无需依赖隐藏的全局运行时 |
| public/views/work.js | 作品总览、材料清单、打印清单 | 独立于事件绑定，可用只读方案测试 |
| public/views/making.js | 制作、成品反馈、历史记录视图 | 视图不负责保存或变更方案 |
| lib/recipe.js | Recipe 构建、购买金额、预算校验与同步 | 从 studio.js 分离，计算只有一份实现 |
| lib/runtime.js | 应用内 API 路由与错误契约 | 从构建脚本字符串移到可阅读、可测试模块 |
| browser/runtime-entry.js | 浏览器依赖装配、目录加载与失败重试 | fetch / baseUrl / version 可注入；失败后允许重试 |
| scripts/bundle-commonjs.js | 将静态 CommonJS 模块打包供浏览器使用 | 递归读取真实依赖；保留模块正文，移除按变量名替换的构建逻辑 |
| scripts/check-syntax.js | 自动发现 JS 文件并检查语法 | 新模块自动进入语法检查，不再手工维护长命令 |

public/runtime.js 仍是生成文件；从 browser/ 和 lib/ 修改源代码后构建。浏览器 API、存储键、IndexedDB 版本、.floralab schema 和已有作品算法保持兼容。旧浏览器哈希算法保持原样；它只用于稳定布局，不作为安全哈希。

### 后续结构演进

应用控制层仍集中在 app.js，按实际页面迭代逐步拆成 exploration-controller、recipe-controller、build-controller 和 handoff-controller。避免仅为了目录整齐继续搬函数。

先形成以下边界：领域规则不操作 DOM 或浏览器存储；视图只读取状态；控制器接收操作、调用领域服务、保存并刷新；存储适配器统一处理错误、恢复与快照。复杂 UI 更新以后可引入框架，但需要先验证收益，当前不做全量框架迁移。

未来增加的领域模块建议为 intent（明确要求与解析证据）、media（图片与事实版本关联）、revision（快照和恢复）、workflow（选定方案及制作状态）。独立模块应同时具备明确输入输出、失败处理和行为测试。

生成物与数据来源也要进一步整理：目前 library.js 仍由 source-parts 拼接，后续按目录、详情、查询与图片来源拆分；材料真实性和图片许可证应继续由数据来源审计保护，不能顺手删掉。

## 8. 数据与 AI 边界

当前 .floralab/2.0 的 Recipe 与 Blueprint 为作品事实；本轮不升级 schema。新增媒体前先设计可迁移扩展：assetId、类型（参考/生成/成品）、方案 ID、事实版本、来源、文件摘要、创建时间、用户核对状态。字段名称为建议，需通过导出兼容设计后再固化。

图片使用 IndexedDB Blob 存储，限制单文件大小和像素并提供压缩；不要把大图片写入 localStorage。导出必须明确包含哪些图片，引用缺失时能够继续导入文本事实。跨设备同步作为独立项目，不以本机保存替代云同步承诺。

AI 只提出候选或生成视觉。任何材料与结构变更经过差异展示、用户操作、领域校验后才能进入事实档案。模型无法完成时，可保留想法、导出交接、手动记录图片，不让作品流程全部失效。

宠物、供水、食品隔离、运输、承重、价格等事实需要可核实依据。没有来源的状态明确为待核实，不用一条笼统“安全”标签替代现实判断。

## 10. 验收方法与效果衡量

自动测试验证数据与行为，截图验证布局，真人任务验证是否看得懂，三者分别记录。当前已完成的是界面审阅与工程检查，尚未开展真人任务研究。

后续邀请 3–5 位与目标场景相符的使用者，不先讲解产品，让他们完成：从一句话建作品；锁住材料另选构图；找到还需购买的清单；按一步制作说明说明怎么做；保存照片并重新打开作品。记录卡住的位置、误点、需要提示次数和完成时间。样本用于发现问题，不代表统计显著结论。

建议验收目标（待验证，不是当前成绩）：

- 首次访问能在 30 秒内说明产品用途和可得到的结果。
- 描述想法后，在不填高级参数的情况下得到可理解的起点；首个有效操作不需要寻找多屏。
- 能正确解释已锁定与允许调整的区别；已锁定事实在所有变体中保持。
- 能指出当前选定方案与备选方案；预览不会生成多余作品。
- 不借助对话解释，找到采购清单并说明下一制作步骤。
- 修改后刷新、离线重开、导出再导入，事实和媒体关联仍一致。

桌面按 100% 实际页面尺度、手机至少 390px 和窄屏检查；补充键盘操作、焦点可见、文字放大、触控目标及状态不依赖颜色。先逐页检查，再看汇总图。发布必须依次完成实现、自动检查、本地逐页、部署、正式线上逐页。

只收集完成研究所需信息；默认不上传用户作品图片和想法文本做分析。将来若增加产品事件统计，先明确用途、保存期限与关闭方式。
